# 测试用例标准

## 必填字段

每条测试用例必须包含：

- 用例 ID
- 模块
- 场景
- 优先级：P0 / P1 / P2 / P3
- 前置条件
- 测试数据
- 操作步骤
- 预期结果
- 来源
- 置信度：confirmed / extracted / inferred / missing
- 自动化建议：适合 / 不适合 / 待评估
- 确认状态：draft / approved / rejected / needs-update
- 落库状态：not-persisted / pending / persisted

## 优先级定义

| 优先级 | 含义 | 执行时机 |
|--------|------|----------|
| P0 | 冒烟路径，失败则阻塞测试或发布 | 每次构建必跑 |
| P1 | 核心业务回归，影响主流程或收入 | 发版必跑 |
| P2 | 模块级回归，影响局部功能 | 相关变更必跑 |
| P3 | 探索、兼容、长尾边界 | 有时间或专项测试时执行 |

## 生成规则

1. 先覆盖 P0 主路径，再补 P1 核心分支。
2. 历史 Bug 高频模块至少生成 1 条回归用例。
3. 权限、支付、订阅、数据删除、状态流转必须覆盖正向和异常路径。
4. 自动化候选优先选择稳定、高频、可断言的路径。

## 人工确认与落库

1. 新生成的测试用例默认状态必须是 `draft`。
2. 新生成的测试用例必须先引导用户确认是否进行审核评分。
3. 审核总分低于 60 分的用例不能标记为 `approved`。
4. 用户人工确认后，才能将确认状态改为 `approved`。
5. 用户拒绝或要求修改的用例必须标记为 `rejected` 或 `needs-update`。
6. 用例必须落库，或生成待落库记录后，才能进入自动化用例评审。
7. 落库目标由 `.qa-agent.yml` 的 `testcase_provider` 配置决定；未配置时，输出本地可落库文件和手动导入说明。
8. 自动化脚本必须引用已确认且已落库的用例 ID。

## 审核评分

用例审核使用 100 分制，60 分为通过线。

执行用例审核前，必须先引导用户确认。

| 维度 | 满分 |
|------|------|
| 逻辑完整性 | 25 |
| 预期结果明确性 | 20 |
| 前置条件完备 | 15 |
| 需求/风险覆盖度 | 25 |
| 边界/异常覆盖 | 15 |

低于 60 分的用例必须输出扣分原因和修改建议，不能进入确认、落库或自动化评审。

## 飞书思维导图导出

当用户明确要求飞书、思维导图或 XMind 导出时，可以将已生成用例导出为飞书兼容 Markdown。

格式要求：

- 第一行允许使用一个 `#` 主标题。
- 标题以下全部使用 `-` 列表项。
- 每级缩进使用 2 个空格。
- 不使用表格、编号列表、`##` 或 `###`。
- 必须保留优先级、前置操作、测试数据、执行步骤、预期结果、来源、置信度、自动化建议、确认状态和落库状态。

推荐结构：

```markdown
# 产品或模块测试用例

- 功能测试
  - TC001-用例名称
    - 优先级
      - P0
    - 前置操作
      - ...
    - 测试数据
      - ...
    - 执行步骤
      - ...
    - 预期结果
      - ...
    - 来源
      - ...
    - 置信度
      - confirmed
    - 自动化建议
      - 适合
    - 确认状态
      - approved
    - 落库状态
      - persisted
```
