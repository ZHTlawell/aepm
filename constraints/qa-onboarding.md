# QA 项目入驻约束

## 目标

帮助测试人员从分散资料中建立可靠的项目认知。入驻结论必须可追溯、可复查、可继续用于风险分析和用例生成。

## 输入资料顺序

1. 项目结构：源码目录、README、启动方式、技术栈、模块边界。
2. 产品概览：定位、目标用户、核心业务闭环。
3. 产品图：页面、导航、关键流程、异常状态。
4. 产品文档：PRD、Speckit、需求 issue、业务规则。
5. 接口文档：API、认证、错误码、第三方依赖。
6. 数据库文档：实体、表关系、状态流转、数据一致性。
7. 测试用例：已有覆盖、优先级、缺口。
8. 历史 Bug：高频问题、易回归模块、遗留风险。
9. 测试报告：最近质量结论、阻塞项、未解决问题。
10. 自动化：覆盖路径、执行方式、稳定性、缺口。

## 完整性评分

默认总分 100：

| 类别 | 分值 |
|------|------|
| 项目结构与启动方式 | 10 |
| 产品概览与业务目标 | 10 |
| 产品图或页面截图 | 10 |
| PRD / Speckit / 需求文档 | 15 |
| API 文档 | 10 |
| 数据库或数据模型说明 | 10 |
| 现有测试用例 | 15 |
| 历史 Bug | 10 |
| 历史测试报告 | 5 |
| 自动化测试说明 | 5 |

低于 60 分时，只允许输出初步理解和缺口清单，不应生成完整回归结论。低于 40 分时，必须建议先补资料。

## 证据要求

关键结论必须包含：

- 结论
- 来源
- 置信度：`confirmed`、`extracted`、`inferred`、`missing`
- 待确认问题

禁止把推断结论写成事实。
