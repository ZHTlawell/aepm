# Skill: 新模块测试任务规划

## 触发条件

当用户提供新模块、新需求、PR、版本说明或测试任务，希望产品专属 QA Agent 基于已有产品理解进行测试任务拆解时触发。

## 输入

- 新模块说明、需求文档、PRD、设计图、接口文档、Git diff 或自然语言描述。
- `.qa-memory/` 中的产品记忆。

## 前置检查

1. 读取 `constraints/product-agent-memory.md`。
2. 检查产品熟悉度是否达到 85。
3. 如果未达到 85，先追问缺失信息，不要直接生成完整测试任务。
4. 检查新模块是否属于当前产品。
   - 如果属于另一个产品，提示创建新的产品 Agent。
5. 如果输入是 PRD、需求文档或需求截图，先执行 `/ae-qa-review-requirements`。
   - 执行前必须先引导用户确认是否进行需求质量评审。
   - 低于 60 分：停止完整测试任务规划，只要求用户先修订最高优先级需求问题。
   - 60-74 分：允许生成有限测试范围和待确认项，不生成完整回归结论。
   - 75 分及以上：可以继续生成新模块测试任务清单。

## 执行流程

1. 基于 `.qa-memory/` 理解新模块与现有产品的关系。
2. 如果有需求评审报告，读取 `qa/13-requirement-review.md`，把 P0/P1 需求问题作为测试风险输入。
3. 识别影响范围：
   - 页面
   - 模块
   - 用户路径
   - API
   - 数据状态
   - 权限
   - 历史风险
   - 自动化覆盖
4. 如果信息不足，按追问策略向用户提问。
5. 生成“可选择的测试任务清单”，让用户选择要执行的任务。
6. 用户选择后，再执行对应任务，不要默认全部展开。

## 输出任务清单

输出 `qa/14-new-module-test-plan.md`：

```markdown

## 新模块理解摘要

## 与现有产品的关系

## 需要用户选择的测试任务

| 编号 | 任务 | 产物 | 建议优先级 | 适用场景 |
|------|------|------|------------|----------|
| 1 | 审核新模块需求质量 | 需求评审报告 | P0 | 用户提供 PRD / 需求文档 |
| 2 | 生成模块测试范围 | 测试范围清单 | P0 | 需求评审通过或有条件通过 |
| 3 | 生成 P0/P1/P2 用例草案 | 测试用例草案 | P0 | 准备执行测试 |

| 6 | 生成接口测试点 | 接口检查清单 | P1 | 有 API 文档 |
```

## 硬规则

- 先让用户选择任务，再执行。
- 不熟悉时必须追问，追问目标是补足模块理解。
- 所有测试任务必须引用产品记忆或新模块资料作为来源。
- 新模块 PRD / 需求文档必须先通过 `/ae-qa-review-requirements`；低于 60 分时不能生成完整测试任务。
- 需求评审前必须先让用户确认，不要自动评审。
- 用例草案必须先通过 `/ae-qa-review-cases` 审核；低于 60 分的用例不能确认、落库或进入自动化评审。
- 自动化用例评审只能基于已确认且已落库的用例。
