# Skill: QA 测试用例生成

## 触发条件

当测试人员已经具备项目理解包和风险地图，需要生成初版测试用例、补齐覆盖缺口、为版本回归生成用例，或将已确认用例导出为飞书思维导图 Markdown 时触发。

如果用户只要求“导出飞书 / 思维导图 / XMind”，不要重新生成用例；应优先读取已确认、已落库或待落库的用例，再执行导出。

## 输入

- `qa/01-product-brief.md`
- `qa/02-module-map.md`
- `qa/03-user-journeys.md`
- `qa/06-risk-map.md`
- 可选：历史测试用例、历史 Bug、变更影响分析。
- 可选：`.qa-memory/`、新模块 PRD、产品图、UI dump、接口文档、数据库说明。
- 可选：`qa/13-requirement-review.md`。
- 可选：已确认用例或用例库导出。

## 执行流程

1. 读取 `constraints/test-case-standard.md`。
2. 如果缺少产品理解包或风险地图，先提醒用户执行对应 skill。
3. 如果本次基于新模块 PRD 生成用例，先检查是否已有需求评审报告；没有则建议执行 `/ae-qa-review-requirements`。
4. 明确本次范围：全产品、某模块、P0 冒烟、核心回归、变更回归或飞书导出。
5. 生成用例草案，先生成 P0 冒烟用例，再生成 P1 核心回归。
5. 对高风险模块补充异常、权限、边界、数据一致性用例。
6. 从历史 Bug 生成回归用例。
7. 每条用例必须标注来源、置信度、自动化建议和落库状态。
8. 输出后只做一件事：询问用户是否进入 `/ae-qa-review-cases` 用例审核评分。
9. 审核分数达到 60 分及以上的用例，才允许用户人工确认。
10. 用户确认后，引导用例落库。落库目标由 `.qa-agent.yml` 的 `testcase_provider` 决定；未配置时输出可落库的本地 Markdown/YAML 草案。
11. 用例确认并落库后，才允许生成自动化候选或自动化评审。
12. 如果用户明确要求飞书、思维导图或 XMind 导出，则把已确认用例导出为飞书兼容 Markdown。

## 输出

写入 `qa/09-test-cases.md`：

```markdown
# 测试用例草案

## P0 冒烟用例

| ID | 模块 | 场景 | 优先级 | 前置条件 | 测试数据 | 步骤 | 预期结果 | 来源 | 置信度 | 自动化建议 | 确认状态 | 落库状态 |
|----|------|------|--------|----------|----------|------|----------|------|--------|------------|----------|----------|

## P1 核心回归

## P2 模块回归

## P3 探索测试

## 自动化候选

## 待人工确认

## 落库清单
```

可选写入飞书思维导图导出：

```text
qa/exports/test-cases-feishu-mindmap.md
```

飞书导出格式必须使用完整列表层级：

```markdown
# 产品或模块测试用例

- 功能测试
  - TC001-用例名称
    - 优先级
      - P0
    - 前置操作
      - ...
    - 测试数据
      - ...
    - 执行步骤
      - ...
    - 预期结果
      - ...
    - 来源
      - ...
    - 自动化建议
      - 适合 / 不适合 / 待评估
```

飞书导出约束：

- 除第一行主标题外，不使用 `##`、`###` 或表格。
- 所有内容使用 `-` 列表项。
- 每级缩进使用 2 个空格。
- 不使用编号列表。
- 不删除来源、置信度、自动化建议和用例确认状态。

## 硬规则

- 每条用例必须有前置条件、步骤、预期结果和来源。
- 不要生成无法执行的泛泛描述。
- 历史 Bug 回归用例必须能验证“修复没有再次失效”。
- 生成结果默认是 `draft`，不能直接视为可执行正式用例。
- 生成后必须先引导用户确认是否执行用例审核评分；低于 60 分的用例不能通过。
- 用例必须经过用户人工确认后才能标记为 `approved`。
- 用例必须落库或生成待落库记录后，才能进入自动化候选评审或脚本生成。
- 自动化建议只能是候选判断，不等于直接生成自动化脚本。
- 飞书思维导图导出只改变展示格式，不改变用例事实、来源和确认状态。
