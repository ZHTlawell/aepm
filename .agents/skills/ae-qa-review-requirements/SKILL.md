# Skill: 需求评审评分

## 触发条件

当用户要求评审需求、审核 PRD、需求文档打分、review 需求，或在新模块测试前需要判断需求是否足够清晰可测时触发。

## 输入

- PRD、需求文档、需求截图、在线文档、需求 issue 或自然语言需求描述。
- 可选：产品图、接口文档、数据库说明、历史 Bug、QA Memory。
- 可选：项目背景、目标用户、版本范围、业务约束。

## 执行流程

1. 读取 `constraints/requirement-review-standard.md`。
2. 先引导用户确认是否进行需求质量评审，不要直接执行完整评审。
3. 用户确认后，解析需求文档结构：
   - 标题与版本
   - 背景与目标
   - 用户角色
   - 功能需求
   - 非功能需求
   - 业务规则
   - 交互流程或状态流转
   - 验收标准
   - 优先级与追溯信息
4. 按 7 个维度评分：
   - 内容完整性
   - 逻辑一致性
   - 清晰无歧义
   - 可测试性
   - 用户场景覆盖
   - 边界与异常处理
   - 可追溯性
5. 输出 P0/P1/P2 问题清单。
6. 对每个关键问题给出具体可执行的改进建议。
7. 如果需求低于 60 分，只引导用户先修订需求，不生成完整测试用例。
8. 如果需求达到 60 分以上，下一步只建议用户选择是否进入新模块测试任务规划。

## 引导话术

评审前默认只引导一个动作：

```text
已收到需求资料。

下一步只做一件事：请确认是否进行需求质量评审。

评审会检查完整性、一致性、清晰度和可测试性。低于 60 分时，不会继续生成完整测试任务。
```

## 与测试流程的关系

- 新模块 PRD 低于 60 分：不进入完整用例生成，只输出缺口和一个最高优先级补充问题。
- 新模块 PRD 达到 60 分但低于 75 分：可生成有限测试范围和待确认项，不生成完整回归结论。
- 新模块 PRD 达到 75 分以上：可进入 `/ae-qa-new-module-test` 任务规划。
- 需求评审报告可作为后续测试用例的来源之一，但不能替代 PRD 原文。

## 硬规则

- 不替需求方重写整份 PRD。
- 不把推断当成已确认需求。
- 改进建议必须具体到可执行，避免“建议完善”“建议细化”等空泛表述。
- 需求低于 60 分时，不允许继续生成完整测试用例。
- 每轮引导只给一个下一步。
- 未经用户确认，不要直接执行完整需求评审。
