# ae-submit-requirement

> 填补"用户有想法"到"AE Team 收到可评估的需求描述"之间的转化环节——让非技术用户也能提出可落地的能力需求。

## 问题陈述

AE Platform 的用户想要新能力时，面临两个核心困难：

1. **需求描述不可执行** — 用户说"想让 AI 帮我做 XX"，但没有使用场景、当前做法对比和验证标准，AE Team 拿到后无法评估工作量，也无法判断"做到什么程度算完成"
2. **需求和 bug 混淆** — 用户分不清"现在的东西坏了"（bug）和"想要一个新东西"（需求），经常把需求当 bug 提，或者把 bug 当需求提，导致优先级误判
3. **一次性任务 vs 可复用能力** — 用户习惯提"帮我做这件事"而非"帮我建一个能重复做这类事的能力"，AE Team 如果照单执行，每次都是定制开发，无法规模化

## 解决方案

一个跨角色（ae-pm + ae-go）的需求提交 skill，通过对话引导帮用户将模糊想法转化为包含使用场景、当前做法、期望效果和验证标准的结构化需求。

核心机制：
- **意图理解** — 先厘清用户想解决什么问题，而非直接问"你要什么功能"
- **结构化引导** — 将需求整理为 5 个维度：需求描述、使用场景、当前做法、期望效果、验证标准
- **验证标准必填** — 如果用户没提供验证标准，主动追问。没有验证标准的需求无法验收
- **自动路由** — 与 ae-submit-bug 共用路由机制，读取当前角色 CLAUDE.md 中的路由表确定目标仓库
- **确认门禁** — 格式化后展示给用户确认，确认后才提交

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|------|------|------|----------|
| 跨角色共享 | 共享（skills/ 根目录） | 与 ae-submit-bug 一致，逻辑完全相同，只有路由不同 | 每角色独立——维护负担 |
| 验证标准必填 | 强制要求至少一条 | "做到什么程度算完成"是需求能落地的前提。没有验证标准的需求等于开放式任务 | 选填——导致大量无法验收的 issue |
| 标题前缀 | `[FEAT] 能力简述` | 与 `[BUG]` 前缀配合，在 issue 列表中快速区分类型 | 无前缀——和 bug 混在一起 |
| 引导"可复用能力" | CLAUDE.md 行为准则第 5 条 | AE Platform 的规模化依赖于能力可复用。一次性任务不应走需求通道 | 不限制——AE Team 沦为定制开发外包 |
| 与 submit-bug 分离 | 独立 skill | 收集的信息维度完全不同（bug 需要复现步骤，需求需要使用场景和验证标准） | 合并为一个"submit-feedback" skill——两种 issue 的引导逻辑差异大，合并会让流程混乱 |

## 已放弃方案

### 方案 A: 需求模板表单
- **是什么：** 一次性展示空白模板，让用户填写
- **为什么放弃：** 非技术用户面对空白模板无从下手。对话式引导可以根据用户已提供的信息跳过已知项，体验更自然

### 方案 B: 合并到 submit-bug
- **是什么：** 统一一个 submit-feedback skill，内部判断是 bug 还是需求
- **为什么放弃：** bug 和需求收集的信息完全不同——bug 需要复现步骤和错误信息，需求需要使用场景和验证标准。合并后流程分支过多，不如分开清晰

### 方案 C: 自动判断 bug/需求
- **是什么：** agent 自动判断用户反馈属于 bug 还是需求，不问用户
- **为什么放弃：** 边界模糊（"这个按钮应该放在更显眼的位置"——是 bug 还是需求？）。让用户自己判断更准确，agent 只在不确定时辅助

## FAQ

**Q: 和 ae-submit-bug 的关系是什么？**
A: 并列的兄弟 skill。submit-bug = "现在的东西坏了"，submit-requirement = "想要一个新东西"。两者共享跨角色架构和路由机制，但收集的信息维度不同。

**Q: 用户提了一个不可复用的一次性任务怎么办？**
A: agent 应引导用户思考：这个需求是否可以抽象为可复用机制？如果确实是一次性任务，说明不适合走需求通道，agent 可以直接帮用户完成（如果在能力范围内）。

**Q: 验证标准写什么好？**
A: 至少一条可执行的验证步骤。好例子："执行 `/ae-xxx`，能看到 XXX 输出"。坏例子："做得好"、"比现在强"。

## 生命周期

- **填补的 gap：** 用户的功能需求缺少结构化表达通道。模糊需求导致 AE Team 评估困难，验收标准缺失导致无法判断"做完了没有"
- **什么会让它过时：** 当 AE Platform 的能力覆盖足够广泛，用户新需求主要通过 override 机制实现（把好的 override 吸纳为默认行为），显式提需求的场景会减少。但全新能力请求仍需此通道
