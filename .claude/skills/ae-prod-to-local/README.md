# ae-prod-to-local

> 已上线产品的代码拿到手后跑不起来，因为公司内部依赖像暗物质一样看不见也绕不开。ae-prod-to-local 用三档分类法把依赖理清楚，让 PM 知道哪些能跑、哪些要找人、哪些能换掉。

## 问题陈述

PM 从其他团队（如杭州团队）拿到已上线产品的源码后，面临三个核心困境：

1. **跑不起来** — 代码依赖公司私有 Maven 仓库、私有 CocoaPods repo、内部 GitLab 的 SSH 访问权限。`pod install` 或 `./gradlew build` 直接失败，PM 不知道该找谁要什么权限
2. **分不清依赖** — 产品代码混用了 30-50 个依赖库，有的是公开的（Alamofire、Kingfisher），有的是公司内部封装（BCNetwork、BCAccount），有的看起来像公开库但实际是私有 fork。PM 无法判断哪些是"公司独有的必须遵守"，哪些是"换个公开库就行"
3. **无法为 ae-dev 提供约束** — ae-dev 生成新产品时需要知道哪些技术选型是"公司必须用的"（如用户认证、支付验证），哪些是"随便选的"。没有依赖分类，speckit 的 constraints 就写不准确

根本原因：**产品代码是"结果"不是"说明书"，它不会告诉你为什么用这个库、能不能换。** PM 需要的是一份带理由的依赖分类表和一个能在本地跑通核心链路的最小环境。

## 解决方案

一个 4-Phase 的分析 + 本地化 skill，核心设计：

1. **三档分类法** — 每个依赖归入 A（不可替代）/ B（可替代）/ C（通用）三档，分类直接决定 ae-dev 生成代码时的约束等级
2. **最小可运行原则** — 不追求 100% 功能跑通，目标是核心链路的最小验证版本。A 类依赖 mock 掉，B 类依赖用公开库替换，C 类依赖直接安装
3. **5 份结构化产出** — dependency-map.md（依赖分类表）、local-run-guide.md（运行指南）、patches/（配置补丁）、team-request.md（找人清单）、constraints-draft.md（speckit 约束草案）
4. **迭代式验证** — Phase 4 按运行指南实际执行，成功/失败实时更新文档，保证产出是经过验证的而非推测的

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|------|------|------|----------|
| 分类粒度 | 三档（A/B/C） | A = 必须约束、B = 建议约束、C = 无需约束，直接映射到 speckit 的 constraints 层级 | 二档（内部/外部）— 无法区分"必须遵守"和"可以换掉"的内部库；五档 — 过细，PM 难以理解和使用 |
| B 类判断方法 | 查看源码找底层依赖 + 评估封装厚度 | 薄封装（只是配置初始化 + 接口转发）可以直接用底层公开库；厚封装（含大量业务逻辑）实质上是 A 类 | 只看包名判断 — 无法区分 BCNetwork（薄封装 Alamofire）和 BCAccount（深度绑定用户体系） |
| 输出格式 | 5 份独立 Markdown 文件 | 每份文件面向不同消费者：dependency-map 给架构师、local-run-guide 给开发者、team-request 给 PM 协调、constraints-draft 给 ae-dev | 单份综合报告 — 太长且混合了不同视角；YAML/JSON — PM 读不了 |
| 本地化策略 | Mock A 类 + 替换 B 类 + 安装 C 类 | 最小化对原团队的依赖，能跑多少跑多少，跑不了的给出精确的"找谁要什么"清单 | 全量搭建 — 需要完整内网权限，PM 通常拿不到；只做分析不跑 — 纸上谈兵，很多问题只有实际跑才会暴露 |
| 产出放置位置 | 项目内 `local-prototype/` 目录 | 与项目代码共存，方便 git commit 追踪变更，其他人 clone 后也能看到 | `~/.ae/` 下 — 跨项目但不跟随项目走，换机器丢失 |
| 验证方式 | 实际执行后标记 ✅/❌ | local-run-guide 中每一步都要实际跑过，避免写出"应该能跑"但实际跑不通的指南 | 静态评估 — 无法发现运行时问题（如端口冲突、版本不兼容） |

## 已放弃方案

### 方案 A: Docker 全量打包
- **是什么：** 让原团队提供完整的 Docker Compose 环境，一键 `docker-compose up` 跑通所有服务
- **为什么放弃：** iOS 应用无法 Docker 化（需要 Xcode + 模拟器/真机）。后端部分可以 Docker 化，但 PM 通常没有原团队的 Docker 镜像仓库权限。此外，Docker 环境隐藏了依赖细节，不利于理解代码结构

### 方案 B: 只做文档分析不做本地化
- **是什么：** 只生成依赖分类表和约束草案，不尝试在本地跑通
- **为什么放弃：** 纸上分析的依赖分类准确率约 70%，很多"看起来是 B 类"的库实际 `pod install` 时才发现有隐式依赖（如 BCNetwork 看起来只封装 Alamofire，但实际还依赖 BCCrypto 做请求签名）。不跑一遍就不知道

### 方案 C: 远程开发环境
- **是什么：** 连接原团队的 dev/staging 环境，iOS 客户端指向远程后端
- **为什么放弃：** 远程环境权限通常更严格（VPN + 跳板机 + 账号申请），且网络延迟影响开发体验。本地化方案让 PM 有完全可控的环境

## FAQ

**Q: 三档分类中 B 类的"封装厚度"怎么判断？**
A: 看源码。如果内部库只有 1 个文件、20-50 行代码、只做了配置初始化和接口转发 → 薄封装（B 类）。如果有多个文件、含业务逻辑（加密、鉴权、协议处理）→ 厚封装，实质上是 A 类。

**Q: 如果私有 repo 权限全部拿不到怎么办？**
A: `pod install` 会失败，但可以手动下载/替换 B 类和 C 类依赖的源码。A 类依赖写 mock（如 `IsVIP()` 直接返回 true）。最终产出的 team-request.md 里会列出"需要原团队提供的最小权限清单"。

**Q: constraints-draft.md 会直接写入 speckit 吗？**
A: 不会直接写入。它是草案，PM 确认后由 `/ae-demo-to-speckit` 或 `/ae-speckit-receive` 引用。A 类约束会成为 speckit 的硬性约束，B 类约束成为建议约束。

**Q: 产品有多个子项目（iOS + 后端 + 配置仓库）怎么处理？**
A: 全部扫描，分别生成依赖分析。local-run-guide.md 按角色分节（后端启动→iOS 启动→联调验证），确保端到端可测试。

## 生命周期

- **填补的 gap：** PM 拿到其他团队的产品代码后，没有系统化的方法将其本地化运行并提炼出 ae-dev 所需的技术约束。依赖分类全靠口头询问，本地环境搭建靠试错
- **什么会让它过时：** 当公司的所有产品都采用标准化的开发环境配置（如统一的 devcontainer + 公开依赖优先策略），或当 ae-dev 已经积累了足够多的产品约束不再需要从源码逆向提取时，本 skill 可以退役
