# ae-submit-bug

> 填补"用户发现问题"到"AE Team 收到可跟进 issue"之间的鸿沟——让非技术用户也能提出高质量 bug 报告。

## 问题陈述

AE Platform 的用户（PM、运营、全员）在使用 agent 时遇到问题，但缺少一个低门槛的反馈通道：

1. **issue 质量低** — 用户描述"用不了"、"有问题"，AE Team 拿到后无法复现，需要反复追问，反馈周期从 1 天拉长到 1 周
2. **issue 去向混乱** — 用户不知道该提到哪个仓库（ae-pm? ae-go? ae-dev?），经常提错地方，导致 issue 被忽略或转移
3. **本地 issue 文件** — 早期 agent 倾向于在项目目录下创建 `issues/` 文件夹写 markdown，AE Team 根本看不到这些"issue"
4. **缺乏归因引导** — 用户不清楚问题出在哪个环节（demo 本身? speckit 提取? 代码生成? 约束缺失?），归因全靠 AE Team 事后分析

## 解决方案

一个跨角色（ae-pm + ae-go）的 bug 提交 skill，通过对话式引导帮用户把问题说清楚，然后自动提交到正确的 Gitee 仓库。

核心机制：
- **渐进式信息收集** — 不一次问完所有问题，根据用户已提供的信息跳过已知项
- **笼统描述拆分** — 检测到"用不了"等模糊描述时主动追问具体表现
- **自动路由** — 读取当前角色的 CLAUDE.md（`~/.ae/<role>/.claude/CLAUDE.md`）中的 Issue 路由表，确定目标仓库
- **截图引导** — UI 类 bug 主动引导用户提供截图
- **确认门禁** — 格式化后的标题和正文展示给用户确认，确认后才提交

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|------|------|------|----------|
| 跨角色共享 vs 每角色独立 | 共享（skills/ 根目录） | submit-bug 的逻辑在 pm/go/dev 完全相同，只有目标仓库不同，由路由表决定 | 每角色一份——维护 3 个几乎相同的文件 |
| 路由表位置 | 读取 `~/.ae/<role>/.claude/CLAUDE.md` | 仓库信息属于角色配置，不是 skill 逻辑 | 硬编码在 SKILL.md 中——角色增加时需要改 skill |
| 渐进式 vs 表单式 | 渐进式对话 | 用户可能已经在对话中提供了部分信息，表单式会重复询问 | 一次性问清所有字段——用户体验差，像填工单 |
| 标题前缀 | `[BUG] 产品名 — 问题简述` | 在 Gitee issue 列表中快速区分 bug 和需求 | 无前缀——和需求混在一起，无法一眼识别类型 |
| 提交方式 | `ae git issues create` CLI | 统一走 ae-git.py，自动处理 credentials/proxy/重试 | 直接 curl Gitee API——需要手动处理认证和错误 |

## 已放弃方案

### 方案 A: 本地 issue 文件
- **是什么：** 在项目中创建 `bugs/` 目录，每个 bug 一个 markdown 文件
- **为什么放弃：** AE Team 不会去翻用户项目目录找 bug 报告。issue 必须在 Gitee 远端才有意义。v0.6.0 明确禁止

### 方案 B: 统一提交到 ae-platform 仓库
- **是什么：** 所有角色的 bug 都提交到 ae-platform 源码仓库
- **为什么放弃：** ae-platform 是内部开发仓库，用户无权访问。用户提交的 issue 应该在用户能看到的仓库（ae-pm/ae-go/ae-dev）

### 方案 C: 自由格式提交
- **是什么：** 用户说什么就直接提交，不做格式化
- **为什么放弃：** "视觉差距大"这样的描述无法指导修复。v0.7.0 引入了笼统描述拆分机制——必须具体到可验证的条目

## 开源供应链

| 组件 | 来源 | 覆盖度 | 我们的增量 |
|------|------|--------|-----------|
| Gitee issue 创建 | ae-git.py（自建 CLI） | 100% API 封装 | 无 — 纯复用 |
| Bug 归因体系 | AE Platform 自建 | 无对标 | DEMO-BUG / SPECKIT-GAP / GEN-BUG / CONSTRAINT-GAP / BUG 五阶段前缀 |
| 路由机制 | AE Platform 自建 | 无对标 | 根据当前角色自动路由到正确仓库 |

本 skill 无外部开源依赖。核心价值在于面向非技术用户的对话式引导和跨角色自动路由。

## FAQ

**Q: ae-submit-bug 和 ae-file-bugs 有什么区别？**
A: ae-submit-bug 是"人→issue"（用户口述一个 bug，agent 引导格式化后提交）；ae-file-bugs 是"报告→issues"（从 verify-app 的 diff report 批量生成 issue）。前者适合日常使用，后者适合验证流程后的批量提交。

**Q: 非 ae 项目 workspace 下提交，issue 会去哪？**
A: 路由由 `~/.ae/<role>/.claude/CLAUDE.md` 中的 Issue 路由表决定，不受当前 workspace 影响。v0.22.3 修复了早期因"查阅当前 CLAUDE.md"导致的路由歧义问题。

**Q: 用户不知道该提 bug 还是需求怎么办？**
A: 问用户"是遇到了问题（现在的东西坏了）还是有新想法（想要一个新能力）？"。前者用 ae-submit-bug，后者用 ae-submit-requirement。

## 生命周期

- **填补的 gap：** 用户和 AE Team 之间缺少标准化的 bug 反馈通道。用户的问题描述质量参差不齐，提交去向混乱
- **什么会让它过时：** 当 AE Platform 拥有自动化的问题检测和上报机制（如 PostToolUse hook 覆盖所有常见错误场景，自动生成可跟进的 issue），用户手动提 bug 的场景会大幅减少。但对于"agent 行为不符合预期"这类主观反馈，仍需人工提交通道
