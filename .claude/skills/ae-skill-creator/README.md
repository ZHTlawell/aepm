# ae-skill-creator

> 标准化 skill 构建流程，确保每个 skill 从创建到发布都经过"跑通→包装→验收"的完整质量关卡。

## 问题陈述

AE Platform 的 skill 质量参差不齐。核心痛点：

1. **写了再跑** — 多个 skill 先写 SKILL.md 再发现核心链路走不通，导致 3-6 个版本迭代才稳定（ae-lark-feishu、ae-demo-to-figma 都经历过）
2. **缺乏设计记录** — 12 个 PM skill 没有一个有 README.md，设计决策和放弃方案全靠口头传承，新维护者接手时完全没有上下文
3. **没有用户视角验证** — 开发者觉得"能跑"但用户说"不好用"，因为只做了 L0-L1 验证（工具能装、命令能执行），没做 L2 验证（用户说 X，agent 做了正确的事）
4. **开源调研缺失** — 有些 skill 自建了通用能力，后来发现开源方案更成熟（如飞书消息从自研迁移到 larksuite/cli），Build vs Buy 决策没有前置

## 解决方案

建立一个 **元 skill（meta-skill）**：用 skill 的方式定义 skill 的构建标准。

核心机制：
- **六段标准** — SKILL.md 必须包含 6 个段落（frontmatter / 身份锚定 / 操作流程 / 硬性规则 / 反模式 / 故障排查），缺一不发布
- **Phase 门禁** — 6 个 Phase 严格顺序执行（需求澄清→核心跑通→写 SKILL.md→写场景→写 README→集成发布），Phase 1 不通过不允许进入 Phase 2
- **审计模式** — 可对已有 skill 进行标准化审计，输出得分和改进建议
- **双层文档分离** — SKILL.md 给 agent 消费（操作指南），README.md 给人类消费（设计文档）

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|------|------|------|----------|
| 六段结构 vs 自由格式 | 六段标准 | 结构化文档让 agent 解析更稳定，也让审计可量化 | 自由格式（agent 理解力够强不需要结构约束）— 实测证明 agent 在无结构时容易遗漏 |
| 验证前置 vs 文档先行 | 验证前置 | 历史数据：先写后跑的 skill 平均需要 4 个版本才稳定 | 文档先行 + 快速迭代 — 迭代成本太高（每次都要 publish） |
| README.md 全中文 | 全中文 | 人类维护者全部是中文母语者，英文文档降低可读性 | 中英混合 — 增加维护负担 |
| 场景验收 5+ 条 | 最少 5 条 | 覆盖正常流程(2) + 边界情况(2) + 错误恢复(1) 的最小集 | 3 条太少（只覆盖正常流程），10 条太多（维护成本高） |
| 审计得分 8 分制 | 4 必须项 + 4 推荐项 | 区分"不可发布"和"可以更好"，避免标准过于严苛导致无法落地 | Pass/Fail 二值 — 无法指导增量改进 |
| 开源调研前置 | Phase 0 做 | VISION.md 原则 2 要求，避免自建通用能力 | 需要时再调研 — 容易错过成熟方案 |

## 已放弃方案

### 方案 A: JSON Schema 强制验证
- **是什么：** 用 JSON Schema 定义 SKILL.md frontmatter 的严格格式，CI 自动验证
- **为什么放弃：** 过于刚性，新 skill 在初期需要灵活调整结构。六段标准是"应该有什么"，不是"字段不能多也不能少"

### 方案 B: 单文件包含所有内容
- **是什么：** 把设计文档、操作指南、场景清单全放在一个 SKILL.md 中
- **为什么放弃：** 文件过大导致 agent token 浪费。agent 执行 skill 时不需要看设计决策和放弃方案，分离后 SKILL.md 可以保持精简

### 方案 C: 自动化 skill 生成（模板填充）
- **是什么：** 提供 `ae skill create <name>` 命令自动生成骨架文件
- **为什么放弃：** 骨架文件会诱导"先填模板再验证"的坏习惯，与"验证前置"原则矛盾。skill 创建应该是思考驱动的过程，不是模板填充

## FAQ

**Q: 简单的 skill 也需要走完 6 个 Phase 吗？**
A: Phase 0-2 和 Phase 6 是必须的。Phase 3（场景清单）和 Phase 4（README）对简单 skill 是"推荐"但非强制。但如果 skill 会被其他人维护，强烈建议补齐。

**Q: 已有 skill 都不符合六段标准怎么办？**
A: 用审计模式逐个检查，按优先级增量补齐。不需要一次性全部达标，但新创建的 skill 必须从一开始就符合标准。

**Q: SKILL.md 和 README.md 内容重复怎么办？**
A: 不应该重复。SKILL.md = "agent 按什么步骤做"，README.md = "为什么这样设计"。如果发现重复，说明 README.md 写成了操作指南，需要重写。

**Q: 开源调研（Phase 0.2）找不到任何方案怎么办？**
A: 正常，说明这是我们的独有价值。在 README.md 的"开源供应链"部分记录"调研日期 + 无对标方案"，后续定期复查。

## 生命周期

- **填补的 gap：** AE Platform 缺少 skill 构建标准化流程。23 个 skill 没有统一的质量基线，新 skill 创建靠个人经验，质量无法保证
- **什么会让它过时：** 当 Claude Code 原生支持 skill 模板和质量门禁（如 `claude skill create` + 内置审计），本 skill 的工具化部分可以退役，但 AE 特有的设计原则（用户无感、开源供应链等）仍需保留
