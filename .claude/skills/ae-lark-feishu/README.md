# ae-lark-feishu

> 填补 Claude Code agent 与飞书生态之间的集成 gap——让用户用自然语言完成飞书消息读写、搜索和会议纪要获取。

## 问题陈述

飞书是 Scale Global 全员的工作沟通平台，但 Claude Code agent 无法直接访问飞书数据：

1. **信息孤岛** — 用户在 agent 对话中需要引用群聊消息、会议决策时，只能手动复制粘贴，无法让 agent 直接读取
2. **会议纪要获取繁琐** — 飞书视频会议的 AI 纪要和逐字稿埋在多层菜单中，需要手动查找 meeting_id → 获取 doc token → 打开文档，非技术用户很难完成
3. **消息搜索效率低** — 在飞书客户端中搜索历史消息功能有限（无法按时间范围精确筛选），agent 可以做得更好

## 解决方案

一个飞书操作的场景编排层 skill，底层委托 larksuite/cli（飞书官方 CLI），自动处理安装引导、认证管理和命令选择。

核心能力（8 项）：
1. **搜索群聊** — 按关键词查找群聊，获取 chat_id
2. **读取群消息** — 拉取指定群聊的消息列表，支持时间范围筛选
3. **搜索消息** — 跨群搜索消息内容，支持发送者/类型/时间筛选
4. **下载图片/文件** — 从消息中提取 file_key 并下载到本地
5. **读取私聊** — 通过 open_id 读取 P2P 对话
6. **发送消息** — Bot 身份发送文本/markdown/图片到群聊或私聊
7. **会议妙记与逐字稿** — 搜索会议 → 获取 doc token → 读取 AI 纪要和完整转写
8. **读取飞书文档** — 通过 doc token 或 URL 读取文档内容

## 设计决策

| 决策 | 选择 | 原因 | 替代方案 |
|------|------|------|----------|
| 底层实现 | larksuite/cli（飞书官方 CLI） | 200+ 命令，覆盖飞书全部 API，官方维护更新及时 | 自研 HTTP 封装（见"已放弃方案"） |
| skill 定位 | 薄封装 + 场景编排 | larksuite/cli 覆盖度 >90%，我们只做安装引导、认证管理、命令选择和输出格式化 | 完全透传（用户直接用 lark-cli）——用户需要记忆命令 |
| 认证方式 | Device Flow（`lark-cli auth login`） | 无需在 agent 中处理 OAuth 回调，用户在浏览器完成授权即可 | App Token 方式——需要用户自行注册飞书应用，门槛太高 |
| 发送消息确认 | 必须用户确认后才发送 | 发送的消息会被其他人看到，是不可逆操作 | 自动发送——风险太高，误发消息无法撤回 |
| 输出格式 | 默认 pretty，需要详情时 json | 展示给用户用 pretty 可读性好；提取 file_key 等详情需要结构化的 json | 统一 json——用户阅读体验差 |
| 从"废弃"回归 | 薄封装而非退役 | VISION.md 原则 1"用户无感"——用户不应被告知去自己装工具，agent 应该包装好给用户用 | 真正退役，让用户直接用 lark-cli 和 MCP（见"已放弃方案"） |

## 已放弃方案

### 方案 A: 自研 HTTP 封装（v0.14.1 初版方案）
- **是什么：** 在 ae-git.py 中封装飞书 OpenAPI，自行处理 OAuth token 刷新、分页、错误重试
- **为什么放弃：** 飞书 API 有 200+ 个接口，自研封装只能覆盖最常用的几个。larksuite/cli 由飞书官方维护，覆盖全部 API 且持续更新。符合 VISION.md 原则 2"通用能力让位给更成熟的开源方案"

### 方案 B: 标记废弃，引导用户直接用 lark-cli + Lark OpenAPI MCP（v0.27.0 短暂尝试）
- **是什么：** 将 ae-lark-feishu skill 标记为 deprecated，SKILL.md 中写迁移指引，引导用户自行安装 lark-cli
- **为什么放弃：** 违反 VISION.md 原则 1"用户无感"——用户说"帮我看飞书消息"，不应该得到"请你先去装 lark-cli"的回答。skill 是隔离层，底层实现变化不应暴露给用户。v0.29.0 回归为薄封装方案
- **教训：** 这个方案只存在了 2 个版本（v0.27.0 → v0.29.0），是 AE Platform "用户无感原则"最直接的实践验证。"退役"概念本身就是错的——除非能力本身不再需要，否则只有"重写底层实现"

### 方案 C: Lark OpenAPI MCP Server
- **是什么：** 配置 Lark OpenAPI 的 MCP Server，让 Claude Code 直接通过 MCP 协议访问飞书
- **为什么放弃：** MCP Server 作为补充方案可以并存，但不能替代 skill 的编排价值。skill 提供的是"搜索会议→获取 doc token→读取纪要"这样的多步工作流编排，MCP 只提供原子 API 调用

## 开源供应链

| 组件 | 来源 | 覆盖度 | 我们的增量 |
|------|------|--------|-----------|
| 飞书 API 访问 | [larksuite/cli](https://github.com/nicepkg/lark-cli)（飞书官方 CLI） | >90%（200+ 命令覆盖 IM/VC/Docs/Contact/Calendar） | 安装引导、认证状态检测、自动重试 |
| 认证管理 | lark-cli auth（Device Flow） | 100% | 前置条件检查 4 步流程、认证失败自动引导 |
| 会议纪要获取 | lark-cli vc + docs | 100% | 多步编排（search → notes → fetch），单命令无法完成 |
| 消息搜索 | lark-cli im | 100% | 参数组合引导（群聊/时间/发送者/类型多维筛选） |

**这是 AE Platform "开源供应链"原则的典型案例。** 自建 HTTP 封装的覆盖度 <10%，larksuite/cli 的覆盖度 >90%。skill 的价值不在于封装 API（开源已解决），而在于：
1. 安装和认证的零门槛引导
2. 多步工作流编排（如"获取会议纪要"需要 3 个命令串联）
3. 用户无需知道底层工具的存在

## FAQ

**Q: 需要飞书管理员权限吗？**
A: 不需要。lark-cli 使用 Device Flow 认证，普通用户授权即可。但访问范围受限于用户自身权限（只能看到自己能看到的群聊和消息）。

**Q: lark-cli 和 Lark OpenAPI MCP 可以同时用吗？**
A: 可以。本 skill 使用 lark-cli 作为底层，Lark OpenAPI MCP 可以作为补充。但 skill 的编排逻辑只基于 lark-cli 命令。

**Q: 为什么发送消息需要 bot 身份？**
A: 飞书 API 限制，通过 API 发送的消息只能以应用/bot 身份发出。用户授权后 lark-cli 自动处理身份切换。

**Q: 消息中的图片为什么需要单独下载？**
A: 飞书 API 返回的消息列表只包含图片的 file_key 引用，不包含图片二进制。需要通过 `messages-resources-download` 命令下载到本地后才能查看。

**Q: 之前的"废弃"通知是怎么回事？**
A: v0.27.0 一度标记为 deprecated 并引导用户直接使用 lark-cli，但这违反了"用户无感"原则。v0.29.0 回归为 lark-cli 的薄封装，对用户来说 skill 从未变化——只是底层实现从自研 HTTP 换成了官方 CLI。

## 生命周期

- **填补的 gap：** Claude Code agent 无法访问飞书数据。用户需要在 agent 和飞书客户端之间来回切换，手动复制粘贴信息
- **什么会让它过时：** 当飞书官方提供原生的 Claude Code 集成（如官方 MCP Server 直接集成到 Claude Code），或者 lark-cli 本身发展为足够智能的交互式工具（用户无需 skill 编排即可完成多步操作），本 skill 的编排层价值会降低。但"安装引导 + 认证管理"的包装层在可预见的未来仍有价值
